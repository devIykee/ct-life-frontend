# Paid character likeness — provider research, 11 October 2026

READY TO COMMIT: `docs/research/paid-character-likeness-20261011.md` — document current likeness provider APIs, constraints and integration plan.

[Inference] This report recommends an implementation and evaluation path. It does **not** establish that any generated model meets CT Life's likeness, animation or mobile-performance requirements. Official pages below were opened on 11 October 2026; no provider account was created, secret inspected, generation purchased, or photo uploaded.

## Decision

**Use Tripo's paid API as the first general-character evaluation adapter. Keep a separate human-reconstruction capability boundary.** Tripo offers reference-image editing, image-to-3D, mesh controls and rigging under one API. This is the best candidate found for the requested human / goblin / shark / whale-humanoid range at a per-job cost, rather than an $800 monthly commitment. Its identity fidelity and preservation of the selected character are unverified. Do not market the result as an exact scan or a drop-in alteration of an arbitrary existing mesh.

**Put “Make it look like me” on the character screen now.** It belongs to the selected identity after wallet sign-in. Outfits remain options within that identity. A custom likeness belongs to the same identity family; it does not become another unrelated roster person. Human and nonhuman modes need different visual acceptance criteria, not separate onboarding locations.

Three production gates remain: an authorized provider account/contract, successful representative 3D samples, and verified purchase fulfillment. A wallet connection alone establishes neither permission to upload a face nor payment for a generation.

## Concrete provider blockers and rights

**Tripo:** Paid-user terms §5.2.2 grant broad output rights and state that paid Inputs/Outputs are not used for AI training. However, §3.2 requires prior written authorization before making its generation service available to end users. Obtain confirmation covering CT Life's embedded paid avatar creation, user-consented photos, selected-character references, downstream image processors, and retention/deletion. A self-serve key is not evidence of that authorization. Free-tier rights are materially different; do not use the free tier for customer likenesses. [Terms](https://www.tripo3d.ai/terms).

**Meshy:** Terms updated 19 September 2026. §2.2 prohibits identifiable input; §2.9 allows non-Enterprise input/output training; §2.5 gives ordinary API output three-day retention. Paid customers own output to the extent law permits under §3.2. These terms make ordinary selfie integration inappropriate without a separate written arrangement. Meshy 5 retired 10 October 2026; legacy `lowpoly` retires 30 October. Do not build new adapters against them. [Terms](https://www.meshy.ai/terms-of-use), [current model parameters](https://docs.meshy.ai/en/api/image-to-3d).

**Avaturn:** Published terms require attribution and commercial-use notification. They also constrain Pro eligibility and describe Enterprise requirements; have the vendor confirm CT Life's eligibility and the right to modify/reuse generated heads on its own cast. The linked privacy policy gives no short fixed photo-deletion SLA or explicit no-training promise; it discusses technology improvement and deletion requests. [Terms linked from Avaturn](https://docs.google.com/document/d/e/2PACX-1vT5_TR6-MNs29LqI-LLKHvIKHVE0iluuapOpHODGRVDaqyfuCsEgaiE3ZIliI1-FN_-9rxJZ3iVo_jJ/pub), [privacy linked from Avaturn](https://docs.google.com/document/d/e/2PACX-1vT-lYthxjPO4SbgkB2kJN8dTFWvRVdF3srOs37oRBgL7IYXK0PAD62u-tF8JXo8ULV6_KVfRW_kuIMo/pub).

**Avatar SDK:** Its public privacy policy allows image data to improve/train computer-vision systems, with named-app exceptions. Do not assume those exceptions cover CT Life's API use. Enterprise terms need an explicit data-processing arrangement and retention policy. [Privacy policy](https://avatarsdk.com/privacy-policy/).

## Proposed Tripo pipeline

[Inference] These are engineering choices, not completed functionality. Preserve provider names/model versions per job so configuration changes do not alter jobs already paid for.

1. **Choose identity → outfit → Make it look like me.** Keep the selected identity, species, outfit and reference revision immutable for a job. Show natural-human or cartoon interpretation copy based on that selected identity. Keep the ordinary roster choice available.
2. **Consent and capture.** Ask for the player's own adult face photos, with a short explanation of named processors and resulting public in-game appearance. Capture/upload only after consent. CT Life should enforce JPEG/PNG, 8 MiB per image, 4096-pixel edge and bounded decoded pixels; these are proposed stricter application limits, not provider limits. Strip EXIF and exclude wallet identifiers from provider payloads.
3. **Reference preview.** Use `POST https://api.tripo3d.ai/v2/openapi/task` with `type: generate_image`, an explicit supported image-edit model, selected identity render plus face reference(s), and a versioned short prompt. Tripo supports multiple image references, `t_pose`, and reference indexing. Proposed first evaluation model: `gemini_3.1_flash_image_preview`. Require the user to approve the reference before the 3D stage. Human: maintain adult human anatomy and distinctive facial shape. Creature: translate those visible traits into the selected creature anatomy. The latter is an artistic interpretation, not facial recognition. [Image generation API](https://docs.tripo3d.ai/image-generation/advanced-image-generation.html).
4. **3D generation.** Submit the approved reference through `image_to_model`, pinned `v3.1-20260211`, `texture: true`, `pbr: true`, `texture_alignment: original_image`, `smart_low_poly: true`, `face_limit: 6000`, `quad: false`. Persist both random seeds. The H3 docs accept JPEG/PNG up to 20 MB and recommend STS object upload. Keep the provider's temporary credentials server-side. `generate_parts` conflicts with textured/PBR generation; do not enable it in this request. [H3 parameters](https://docs.tripo3d.ai/model-generation/image-to-model-v3-0-v3-1.html), [STS upload](https://docs.tripo3d.ai/file-upload/upload-in-sts.html).
5. **Rig and verify.** Complete mesh edits before `animate_prerigcheck`, then `animate_rig` with `model_version: v2.5-20260210`, `rig_type: biped`, `spec: tripo`, `out_format: glb`. A whale or shark choice must be authored as a clear humanoid biped for this route. Tripo's own guidance prefers separated, clear limbs and warns about unusual bodies. Do not infer a valid rig just from a successful mesh task. [Pre-rig check](https://docs.tripo3d.ai/animation/pre-rig-check-v2-0-20250506.html), [rig API](https://docs.tripo3d.ai/animation/rig-v2-5-20260210.html).
6. **Fetch into controlled storage immediately.** Poll the recorded task rather than resubmitting a timed-out POST. Treat `failed`, `banned`, `expired`, `cancelled`, and `unknown` distinctly. Default output URLs expire after five minutes and task queries require the same API key used to create them. Copy approved results, record a content hash and actual `consumed_credit`, then serve only CT Life's own bounded artifact URLs. [Task lifecycle and outputs](https://docs.tripo3d.ai/task-query/get-your-task-result.html).
7. **Prepare and preview the actual playable result.** Normalize scale, upright axis, root origin, skeleton mapping, materials, UV atlas and texture size. Retarget CT Life's existing idle/walk/run rather than buying new animation clips per customer. Validate the 3D result in a rotating preview with idle and walk before acceptance. Preserve the current avatar if generation or import fails.

The listed mesh parameters produce a new mesh. They do not alter the chosen existing mesh in place. If a custom face must retain the exact original body, wardrobe weights and skeleton, build a per-identity deformation/texture-transfer pipeline with artist-authored attachment topology. A generic image-to-3D call does not establish that capability.

For the direct-byte upload adapter, the current official Python SDK uses multipart `POST /v2/openapi/upload` with field `file` and reads `data.image_token`. An older/search-cached documentation example showed `/upload/sts`, while the current HTML extraction omits its endpoint code. Follow the current SDK and require a real-key upload smoke check before enabling. The preferred STS route is `POST /v2/openapi/upload/sts/token`. [Official upload implementation](https://github.com/VAST-AI-Research/tripo-python-sdk/blob/master/tripo3d/client_impl/aiohttp_client_impl.py), [STS implementation](https://github.com/VAST-AI-Research/tripo-python-sdk/blob/master/tripo3d/client.py).

Avatar SDK explicitly offers a quoted custom pipeline to attach its generated heads to a supplied body with texture blending. This is a more appropriate escalation if exact original-body preservation is required and generic generation fails visual tests; the public FAQ does not demonstrate a cartoon goblin/shark version of that pipeline. [Official custom-body FAQ](https://avatarsdk.com/faq/).

## Cost and payment boundary

The opened API price table shows H3 textured generation at 30 credits, smart-low-poly +10, rig 25, and image editing at 5 or 10. A basic edited textured rigged attempt therefore starts around **70–75 credits ($0.70–$0.75)**. The same docs list texture-quality surcharges, including standard +10; reserve **85 credits ($0.85)** for the proposed path until actual `consumed_credit` establishes exact billing. Conversion, retries, additional image previews, storage, processing and payment fees are extra. Do not quote a retail price from these raw costs. [Official API pricing](https://docs.tripo3d.ai/get-started/pricing.html).

[Inference] Use a server-owned quote and separate verified likeness entitlement. A connected wallet and a client-supplied transaction signature are insufficient. A confirmed eligible payment consumes one entitlement atomically and creates at most one generation job. Persist provider task IDs before moving stages; reconcile uncertain submission outcomes instead of blindly issuing another paid request. Reserve bounded retry credits and define replacement/refund behavior before enabling purchases. Keep local development entitlements separate from production verification. No charging or production deployment was authorized in this research subtask.

## Privacy and deletion contract

Tripo's public policy retains inputs/results as necessary and provides deletion subject to its process; it supplies no fixed per-job deletion deadline in the opened API docs. Its help center specifically cautions against uploading third-party face data. Our user's consent and provider's application authorization both matter. Never claim “deleted from everywhere after 24 hours” without a provider agreement and deletion evidence. [Privacy policy](https://www.tripo3d.ai/privacy), [official data handling guidance](https://www.tripo3d.ai/help/privacy-policy/how-to-understand-data-privacy-and-ai-training-at-tripo).

[Inference] Proposed CT Life contract: raw photos expire from CT Life storage after processing, with a maximum 24-hour local retention window; originals stay out of logs, analytics, object names and public CDNs. The UI identifies all processors before upload. Deleting a likeness removes our source images and published assets, restores a stock identity, requests provider deletion, and records completion or failure. Provider-side retention must be stated separately until contractually fixed. No photos, face embeddings, authorization tokens or image URLs with credentials belong in Walrus memory.

## Runtime gap and acceptance evidence

The inspected `client/Packages/manifest.json` has no glTF runtime importer. Returning a GLB URL does not currently produce a playable CT Life avatar. Unity's official glTFast supports runtime loading, custom downloading/material generation, frame-budget scheduling and disposal. The opened versioned documentation is **6.14.1**, not proof that it is the latest release; check registry compatibility before adding it. Use a controlled importer or a server-built, platform-specific asset bundle. FBX export alone is not a runtime loading solution. [Unity runtime loading docs](https://docs.unity3d.com/Packages/com.unity.cloud.gltfast@6.14/manual/ImportRuntime.html).

[Inference] Acceptance must include consented representative faces across skin tones, head shapes, hair and facial hair; normal human, goblin and aquatic humanoid choices; front/profile/three-quarter likeness review; actual rigged idle/walk/run; outfit clipping; same identity after restart; retry and payment idempotency; and Seeker memory/frame-time tests. The current project spec targets LOD0 4–6k triangles and a 512² atlas, 1024² for a hero character. Validate actual imported counts rather than trusting `face_limit`. A generated portrait is not evidence of any of these 3D criteria.

## Exact configuration still needed

- `TRIPO_API_KEY` in backend-only secret storage, with a **paid** API account and a bounded evaluation budget; never in Unity or committed files.
- Written provider authorization for CT Life's end-user photo-to-avatar use and the agreed data-processing/deletion terms; record a nonsecret agreement reference, not its credential material.
- Pinned image model, mesh model, rig model and per-identity reference/prompt revisions. Fail closed if a chosen provider model is retired.
- CT Life private upload storage, published-asset storage, cleanup worker and metadata-size limits.
- Verified likeness-payment product/fulfillment and refund/retry policy. No inherited game-cash top-up behavior may silently stand in for this.
- A tested runtime asset importer and approved 3D sample evidence. Neither is demonstrated by this research.

The frontend entry, identity/outfit organization, draft preservation, backend job schema, consent record and failure states can be implemented while these configuration gates remain explicit. They must not falsely report that likeness generation is ready or paid for.
