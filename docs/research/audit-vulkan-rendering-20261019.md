## Current rendering path and budget gaps

- URP forward renderer, SRP Batcher enabled, dynamic batching disabled, HDR/depth/opaque texture disabled,2xMSAA. Thermal sample render scale0.6; authored asset0.7. Island supplies a70m main-light shadow distance.
- Render Graph is enabled: the serialized current `RenderGraphSettings.m_EnableRenderCompatibilityMode` is0 and installed URP reads its inverse. The obsolete top-level `m_EnableRenderGraph:0` is migration data, not the active switch. `m_UseNativeRenderPass:0` on the legacy renderer is not proof that no merged native render pass is used by Render Graph.
- Island near cells load within420m and unload beyond560m; terrain has64m chunks with2/4/8m LODs and16m far terrain. A global three-chunks-per-frame budget limits construction work, not submitted GPU geometry. Camera far plane is5200m; terrain/road/building cull distances are0 (far plane).
- `IslandInstanceRenderer` culls48m chunks, then batches all selected instance matrices by prototype/LOD with a24m frustum expansion. A chunk touching the view or near LOD threshold submits all its instances at that chunk's selected tier. Each draw overrides `worldBounds` to an8000m cube around the camera; the bound does not give Unity a useful per-batch spatial rejection. There is no per-frame or per-pass vertex budget, nor telemetry attributing submitted triangles to instance kind/LOD. `FpsMeter` samples only total draw/batch/triangle counters.
- A separate contract concern deserves a focused test: the renderer batches up to1023 matrices, while official Unity6000.3 docs specify511 by default when both objectToWorld/worldToObject are present. Current island shaders do not request `assumeuniformscaling`, and source matrices allow different vertical/horizontal scales, so adding that pragma would not preserve current transforms. Installed shader support also contains a250-entry default for mobile Vulkan when flexible arrays/overrides are absent. Native splitting, actual stage occupancy and corruption from oversized submissions have not been measured; do not claim this is the flash cause or arbitrarily change the limit without a receipt.
- `CTWorldSky.shader` is one gradient/cloud texture shader; it does not intentionally emit neon rectangles. It computes cloud UV using division by`h+0.18` even below the visible cloud range. This exposes an arithmetic singularity at that direction, but no data connects it to the upper-sky band; retain as a secondary isolated shader test only.

## Primary-source research

Opened current Unity6000.3 documentation and the issue page, including fetching the issue's canonical page after the old URL redirected:

1. [Vulkan](https://docs.unity3d.com/6000.3/Documentation/Manual/vulkan.html): supported Android API, per-device filtering, validation guidance. This does not specify the exact engine warning threshold.
2. [RenderMeshInstanced](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/Graphics.RenderMeshInstanced.html): groups are culled/sorted by aggregate bounds; the documented maximum depends on instance data, default511 with both matrices. One call does not mean low vertex work.
3. [Render Graph introduction](https://docs.unity3d.com/6000.3/Documentation/Manual/urp/render-graph-introduction.html): on tile-based mobile GPUs it may combine passes into one native render pass. Low draw-call count does not establish a low per-pass vertex footprint.
4. [UUM-79031, skybox flicker under Vulkan](https://issuetracker.unity.com/issues/18950/skybox-flickers-when-using-the-vulkan-graphics-api-on-certain-devices): intermittent skybox fault reproduced on Pixel7/Mali-G710, reports6000.0.17f1, lists GLES3 workaround; current page lists Won't Fix statuses including6.3.X. It is not a Seeker/Mali-G615 reproduction, so neither cause nor workaround success transfers automatically. No exact current official match for the vertex-data warning's threshold or repair was found.
