# Startup room ownership audit — 2026-10-06

The current controller cancellation boundary does not own resources created by an uncooperative room service. The concrete service races below justify a narrow Realtime candidate. The separate venue/scene/voice and same-controller sign-out races remain open; this candidate must not be described as complete startup-lifecycle acceptance.

## Source-backed interleavings

| Boundary | Reproducible ordering in current source | Consequence and candidate scope |
|---|---|---|
| Flow → city/market join | Flow awaits `_owner.Wait(rt.ConnectCity())`; its owner is destroyed; the SDK join completes afterward. `FlowLifetime` observes a late task but does not close its result. Realtime assigns City/Market after its await. | An obsolete channel can become published after UI teardown. Staged Flow passes its cached owner token; the Realtime/RoomChannel boundary validates before publishing/handler registration. |
| DisconnectAll → pending join | Start city, market or venue join; call DisconnectAll while its property is still null; complete the earlier SDK join. | The baseline disconnect misses that unassigned resource, which later republishes. Staged slots invalidate pending attempts synchronously; late raw SDK results receive Leave on their own handle. |
| DisconnectAll → successor room | An old market leave is pending; start a new city/market join; complete that successor before the old disconnect resumes. Baseline rereads shared Market/City and clears them after awaits. | The earlier disconnect can clear or leave a successor. Staged disconnect detaches and captures all three old handles before its first await, and never selects a cleanup target from shared properties afterward. |
| Concurrent venue joins / leave event | Join or leave venue A, start B, then finish A. Baseline can assign A after B or emit an old VenueLeft after B joined. | Staged per-slot attempt/revision ownership rejects obsolete results and suppresses stale leave notifications. |
| VenueSession.Enter → late Begin | Enter assigns Current before Begin. Begin awaits loader work and JoinVenue before adding world objects and channel subscriptions. Exit has no startup-generation guard; if Channel is not assigned yet it does not call LeaveVenue. | A destroyed or superseded visit can continue after an await. Realtime protection helps when another join/disconnect supersedes its slot, but normal Travel still supplies no venue owner token. No VenueSession patch is included. |
| Late VenueSession.Exit → global services | Exit looks up the current VoiceService and IRealtimeService, calls global Disconnect/LeaveVenue, then unloads a loader that modifies shared camera/scene/lighting state. | Calling this method blindly to clean up a late visit could affect a newer visit. ## Current API evidence

The installed Colyseus package reports version 0.18.8. Its [Client source](../../client/Packages/io.colyseus.sdk/Runtime/Colyseus/Client.cs) exposes `JoinOrCreate<T>(roomName, options, headers)` with no CancellationToken parameter. Its [Room source](../../client/Packages/io.colyseus.sdk/Runtime/Colyseus/Room.cs) exposes `Leave(bool consented = true)`, sends the leave request and waits for closure or its existing five-second timeout. The candidate does not invent an SDK cancellation overload or alter that package.

The current official [Colyseus client documentation](https://docs.colyseus.io/sdk) and [Unity guide](https://docs.colyseus.io/getting-started/unity) document awaiting the room object and leaving that room explicitly. [Connection lifecycle guidance](https://docs.colyseus.io/sdk/connection) distinguishes consented leave from a dropped connection. [Unity 6.3 destroyCancellationToken](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/MonoBehaviour-destroyCancellationToken.html) requires retaining the token while the object exists. [.NET cancellation guidance](https://learn.microsoft.com/en-us/dotnet/standard/threading/cancellation-in-managed-threads) describes cooperative cancellation; cancelling an outer wait is not proof the underlying operation stopped.

## Narrow staged correction and evidence

The [candidate](../../art/gameplay-candidates/realtime-startup-ownership-20261006/README.md) contains four narrow patches (RealtimeService, RoomChannel, IRealtimeService declarations and two Flow call arguments) plus one new internal RoomJoinSlot source. Public request names, room names and token/venueId options remain unchanged. Optional CancellationToken arguments are frontend plumbing, not contract endpoints. No backend, package, wallet, payout, microphone, generated model or live source was changed by this task.

The slot owns only its pending attempt and accepted channel. Newer attempts invalidate predecessors; disconnect invalidates all slots and takes their old handles synchronously. After an uncancellable SDK operation completes, RoomChannel validates the attempt before assigning its Room or installing handlers. Cleanup requests Leave on that exact result. Existing SERVER_BUSY backoff remains, with a cancellable timer; a cancelled older realtime retry cannot hide a newer realtime attempt's busy state. Cross-transport busy-indicator aggregation is not redesigned.

Full actual Net/World/UI/App sources compile against installed dependencies in Editor, Android development and production modes. Sixty-five deterministic assertions execute the actual staged slot, service and RoomChannel source with in-memory SDK and Unity-timer doubles. They cover pre-cancel, late owner cancellation, all three pending slots at disconnect, successor preservation, identity change, exact venue options, leave notification order, non-busy error propagation/recovery, busy cancellation/recovery and direct-channel leave during a pending join. Two negative controls fail at their intended assertions: raw handler registration without the stale-result guard, and clearing a successor after an earlier disconnect await.

These checks do not exercise an actual Colyseus socket or native Unity callback scheduler. The package's real Leave acknowledgement/timeout and physical network failure remain separate acceptance. The policy is main-thread ownership, matching its Unity callers; arbitrary multithreaded callers are not supported/tested. Already-accepted service rooms do not become controller-owned merely because a join token was passed. Shared service replacement/disposal, venue/scene/voice ownership, same-owner sign-out and normal online startup still need their own review and tests.

Independent read-only review found no additional concrete successor-cleanup defect in the candidate's normal awaited paths. Review covered captured candidate cleanup, `_pending` reference identity, all-slot detach before disconnect awaits, leave notification revisions and validation before raw SDK handler publication. Same-user sign-out/rejoin remains the documented separate generation problem. Existing established rooms still finish their ordinary leave sequence; the candidate does not claim immediate shutdown of every established channel callback or a completed physical socket close.
